## 1. Архитектурный стек и системные ограничения

### 1.1. Базовый технологический стек
- **Next.js 16 (App Router, Turbopack)**:
  - Серверные компоненты (RSC) являются дефолтным слоем выборки данных. Запрещено использовать клиентские компоненты (`"use client"`) на страницах маршрутов верхнего уровня (`page.tsx`), кроме редких случаев чисто интерактивных экранов (например, полноэкранный холст Студии).
  - Директива `"use server"` используется **исключительно** для асинхронных серверных экшенов. Запрещено экспортировать из `"use server"` файлов константы, типы или схемы Zod.
- **React 19**:
  - Использование современных примитивов (`useTransition`, `useActionState`, Actions).
  - Никаких устаревших паттернов мутаций через сырые `useEffect` с ручным выставлением стейтов загрузки, если это покрывается Actions/Transitions.
- **Tailwind CSS v4**:
  - Стилизация строится строго на CSS-first конфигурации через токены дизайн-системы платформы (`surface`, `status`, `brand`). Запрещен инлайн-хардкод произвольных hex-цветов, не входящих в палитру проекта.

### 1.2. База данных: Prisma 6 + Neon PostgreSQL
- **Реляционная целостность и запрет на каскадный хаос**:
  - Внешние ключи между критическими сущностями проектируются с правилом `onDelete: Restrict` либо обрабатываются явно.
  - **Категорически запрещено** удалять ключевые сущности (курсы, темы, вопросы, пользователей) через прямое удаление одной строчки в базе.
  - Все сложные каскадные удаления производятся **исключительно внутри транзакции `prisma.$transaction`** с пошаговой контролируемой зачисткой зависимых сущностей:
    * Удаление темы $\implies$ удаление связей пререквизитов (`TopicPrerequisite`), записей разметки графа (`DefaultGraphLayout`, `UserGraphLayout`), попыток квизов (`UserQuizAttempt`), очередей карточек (`UserQuestionReview`), вопросов с переводами и прогресса пользователей с декрементом счетчика темы.
    * Удаление курса $\implies$ атомарная зачистка всех тем, тиров, коллабораторов, покупок/зачислений.

### 1.3. Safe Server Actions Pipeline (Result Pattern)
Все клиентские мутации данных обязаны проходить через типизированный пайплайн `createSafeAction`:
```typescript
export type ActionResult<T> =
  | { success: true; data: T }
  | { success: false; error: ActionError };
```
- **Правила реализации Server Actions**:
  1. **Строгая Zod-валидация каждого входа**: Ни один байт данных от клиента не передается в базу данных или сервисный слой без предварительной схемы `schema.safeParseAsync`.
  2. **Никаких открытых `throw` внутрь клиента**: Серверный код ни при каких обстоятельствах не должен выбрасывать необработанные исключения наружу.
  3. **Доменные ошибки через `ActionException`**: Бизнес-ошибки (`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `BAD_REQUEST`, `CONFLICT`) выбрасываются через `ActionException(code, message)` и мапятся в структурированный `{ success: false, error }`.
  4. **Маскирование непредвиденных сбоев**: Любое непредвиденное исключение логируется на сервере, а клиенту возвращается обезличенный код `INTERNAL_SERVER_ERROR`.
  5. **Проброс системных ошибок фреймворка**: Ошибки `NEXT_REDIRECT` и `NEXT_NOT_FOUND` должны беспрепятственно пробрасываться дальше для штатной работы роутера Next.js.

### 1.4. Zero-Trust Security Model
- **Изоляция секретов и ответов на сервере**:
  - Эталонные правильные ответы квизов (`correctAnswerIndexes`, `correctValue`, regex-паттерны, скрытые тест-кейсы кода) изолированы на сервере в базе данных.
  - Клиентские DTO (`QuizQuestionDTO`) **никогда не содержат** информации о правильности ответов, подсказок или ключей валидации до тех пор, пока сервер не завершит проверку сабмита.
  - Поле `explanation` (разбор вопроса) передается клиенту **только** в составе результатов завершенной попытки `QuizResultDTO`.
- **Защита от накрутки опыта (XP Anti-Exploit)**:
  - Опыт за тему начисляется строго один раз при первом успешном завершении (`isFirstCompletion = true`).
  - Повторные прохождения тем и пересдачи квизов (`retakeQuizAction`) на сервере принудительно возвращают `xpEarned = 0`.
  - Попытка подделки параметров опыта на клиенте невозможна: расчет и начисление очков происходят исключительно в серверном коде транзакции.

## 2. Доменная гибкость Quiz Engine (ЗАПРЕТ НА ХАРДКОД)

> [!CAUTION]
> **КАТЕГОРИЧЕСКИЙ ЗАПРЕТ НА ХАРДКОД ТИПОВ ВОПРОСОВ**:  
> Запрещается писать жесткие конструкции `if (type === "SINGLE_CHOICE") ... else ...`, размазанные по компонентам и серверным сервисам.  
> Система тестирования и оценки знаний Notis проектируется **СТРОГО на базе полиморфного паттерна Strategy / Registry**.

### 2.1. Поддерживаемые типы вопросов
Движок квизов поддерживает полиморфный набор типов:
1. `SINGLE_CHOICE`: Одиночный выбор из предложенных вариантов.
2. `MULTIPLE_CHOICE`: Множественный выбор правильных вариантов (все правильные без лишних).
3. `SHORT_ANSWER`: Текстовый ввод краткого ответа (сверка по точной строке / нормализованному шаблону).
4. `CODE`: Написание программного кода с проверкой через тесты.
5. `FLASHCARD`: Двусторонняя карточка для самопроверки и тренировки памяти.

### 2.2. Архитектура Question Strategy / Registry
Каждый тип вопроса инкапсулируется в независимую стратегию, регистрируемую в едином реестре:
```
src/modules/quiz/
├── strategies/
│   ├── single-choice/
│   ├── multiple-choice/
│   ├── short-answer/
│   ├── code/
│   └── flashcard/
├── registry.ts        # QuestionStrategyRegistry
├── types.ts           # Базовые контракты стратегий
└── services/          # Сервисы оркестрации оценки
```

### 2.3. Требования при реализации или добавлении типа вопроса
Каждая стратегия вопроса обязана предоставлять 4 фундаментальных компонента:
1. **Zod-схема конфигурации и ответа**:
   - Схема данных вопроса в базе данных / редакторе (варианты, правильный ответ, метаданные).
   - Схема ответа пользователя (валидация клиентского ввода перед проверкой).
2. **Серверный Evaluator (чистая функция/класс)**:
   - Контракт: `evaluate(questionData, userSubmission) -> EvaluationResult`.
   - Не имеет побочных эффектов I/O, возвращает `{ isCorrect: boolean, score: number, feedback?: string }`.
   - Защищен от утечки правильных ответов.
3. **Клиентский Input-компонент в фабрике**:
   - Рендерится внутри `QuizStepper` через реестр компонентов по ключу типа вопроса.
   - Унифицированный интерфейс пропсов: значение ответа, callback `onChange`, состояние блокировки (`disabled`), состояние отображения результатов.
4. **Форма в Студии (`StudioQuestionEditor`)**:
   - Компонент настройки вопроса для авторов курсов в боковой шторке Студии.
   - Позволяет автору валидно сконфигурировать вопрос согласно Zod-схеме типа.

### 2.4. Инвариант расширения
- Запрещено реализовывать новый тип вопроса в отрыве от общей стратегии или изменять интерфейс существующих типов, приводя к регрессии.
- Добавление типа вопроса не должно требовать переписывания контейнеров `QuizContainer`, `QuizStepper` или базового пайплайна сабмита.

## 3. Roadmap & Graph Engine

### 3.1. Строгий ориентированный ациклический граф (DAG)
- Образовательный роадмап курса Notis математически представляет собой **Directed Acyclic Graph (DAG)**.
- Направление ребра: `source` (пререквизит) $\to$ `target` (зависимая тема). Тема `target` может быть открыта только после освоения `source`.
- Циклы в графе любой длины недопустимы, так как делают невозможным разблокировку тем для студента.

### 3.2. Обязательный DFS Cycle Guard
- Любая операция создания или модификации связи между темами (`connectPrerequisiteAction`) **обязана проходить валидацию через алгоритм поиска в глубину**:
  ```typescript
  wouldCreateCycle(existingEdges, { source: prerequisiteId, target: topicId })
  ```
- **Алгоритмический инвариант**:
  1. Рефлексивная проверка: соединение темы с самой собой ($A \to A$) немедленно отклоняется.
  2. Транзитивная проверка через DFS: если в графе уже существует путь от `target` к `source`, добавление ребра $source \to target$ замкнет цикл и отклоняется с кодом ошибки `CONFLICT`.
  3. Только при возврате `false` операция разрешается к записи в БД.

### 3.3. Уровни курса (Course Tiers) и Fog of War
- Темы группируются по уровням (`CourseTier`), задающим визуальные и логические этапы освоения программы.
- **Движок тумана войны (Fog of War Engine)** рассчитывает статус каждого узла детерминированно:
  - `COMPLETED`: Тема пройдена (квиз сдан $\ge 80\%$ или нажат «Я освоил материал»).
  - `IN_PROGRESS`: Тема начата, но не завершена.
  - `AVAILABLE`: Все опубликованные строгие пререквизиты (`DependencyType.REQUIRED`) имеют статус `COMPLETED`, либо у темы нет пререквизитов (корневой узел).
  - `LOCKED`: Хотя бы один строгий пререквизит не завершен. Доступ к контенту темы заблокирован.

## 4. Spaced Repetition System (SuperMemo-2)

### 4.1. Математическая модель SM-2
Алгоритм вычисления интервалов повторения является инвариантом платформы и рассчитывается строго по формулам:
- Оценка студента $q \in [0, 5]$.
- Фактор легкости ($EF$):
  $$EF' = \max\left(1.3, \; EF + \left(0.1 - (5 - q) \cdot (0.08 + (5 - q) \cdot 0.02)\right)\right)$$
- Интервал повторения ($I$, в днях):
  $$I(n) = \begin{cases} 
  1, & \text{если } q < 3 \quad (\text{сброс цикла, } n=0) \\
  1, & \text{если } q \ge 3 \text{ и } n = 0 \\
  6, & \text{если } q \ge 3 \text{ и } n = 1 \\
  \text{round}(I(n-1) \cdot EF'), & \text{если } q \ge 3 \text{ и } n \ge 2
  \end{cases}$$

### 4.2. Источники пополнения колоды повторения
Колода повторения студента (`/practice`) формируется из двух согласованных источников:
1. **Автоматическое пополнение**: При завершении темы вопросы квиза и тезисы автоматически регистрируются в таблице `UserQuestionReview` с датой `reviewDueAt = now()`.
2. **Ручное пополнение через Flashcard Builder**: Создание авторских карточек `FLASHCARD` (`admin-flashcard-actions`), которые привязываются к теме и автоматически попадают в очередь студентов, завершивших данную тему.

### 4.3. Согласованность очередей повторения
При обновлении или удалении карточек автором в Студии связанные записи в `UserQuestionReview` должны синхронизироваться, предотвращая появление битых ссылок на несуществующие вопросы.

## 5. Контроль качества и Quality Gates

### 5.1. Пайплайн валидации (`pnpm validate`)
Перед завершением любой задачи, внесением коммита или передачей работы пользователю **обязателен успешный прогон команды**:
```bash
pnpm validate
```
Данная команда запускает полный трехступенчатый контроль качества:
1. `pnpm typecheck` (`tsc --noEmit`): Проверка отсутствия ошибок типов TypeScript со строгими настройками.
2. `pnpm test` (`tsx --test 'src/**/*.test.ts'`): Запуск всего набора модульных и интеграционных тестов.
3. `pnpm build` (`next build`): Продакшн-компиляция проекта через Turbopack, валидация серверных/клиентских баундрис и генерация маршрутов.

### 5.2. Zero-Regression Policy (Политика нулевой регрессии)
- В репозитории зафиксировано **185+ активных тестов**. Ни один существующий тест не должен быть сломан, проигнорирован (`test.skip`) или удален ради прохождения пайплайна.
- Любые архитектурные или доменные изменения обязаны сопровождаться новыми юнит-тестами, покрывающими:
  - Валидацию схем Zod (позитивные и негативные кейсы).
  - Поведение Safe Actions при невалидном вводе и ошибках доступа.
  - Чистую бизнес-логику (расчет очков, SM-2, поиск циклов, оценка квизов).
